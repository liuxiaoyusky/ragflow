# Official Image First Principle
# 官方镜像优先原则

## 核心信念

> "自建镜像是技术债，不是资产。"

**适用场景：** 所有基于开源项目的容器化部署

---

## 五层决策框架

### 1. 真问题过滤

- 官方镜像真的不能满足？
- 需求在生产环境真实存在？
- 上游是否有标准方式？

❌ "理论上可能需要" → 不是真问题  
✅ "生产在用且不可替代" → 真问题

---

### 2. 数据结构优先（按优先级）

#### ✅ 配置解决（最优）
- 环境变量
- 配置文件挂载
- 启动参数

#### 🤔 单文件挂载（可接受）
- ≤3 个独立文件
- 无复杂依赖
- 不依赖需挂载的基础模块

#### ❌ 目录挂载（拒绝）
- 一旦挂载目录 = 模拟自建镜像
- 不如直接自建（至少诚实）

#### ❌ 自建镜像（最后手段）
- 真需求 → 提 PR 给上游
- 上游不接受 → 重新评估需求
- 确实需要 → 承认这是维护负担

---

### 3. 复杂度审查

**计分规则：**
```
环境变量          = 0.1
配置文件挂载      = 0.5
单文件源码挂载    = 2
目录挂载          = 10
自建镜像          = 50
```

**目标：** 总分 ≤ 5

---

### 4. 破坏性分析

**必答问题：**
- 现有数据兼容？
- 用户习惯改变？
- 能否无缝回滚？

**安全模式：** 新分支迁移，保留旧分支作为回滚点

---

### 5. 实用性验证

- 启动速度可接受？
- 升级流程简单？（改一行配置）
- 6个月后还能维护？

❌ 自建镜像：检查依赖、重构建、回归测试  
✅ 官方镜像：pull 新版本

---

## 操作清单

### 迁移前评估
```bash
find . -name "Dockerfile*"                    # 有？需要迁移
grep -r "volumes:" docker-compose.yml | wc -l # >10？太复杂
grep "\.py\|\.js" docker-compose.yml          # >3？重新设计
```

### 标准迁移流程
```bash
# 1. 新分支
git checkout -b official-image

# 2. 纯官方镜像
RAGFLOW_IMAGE=official/project:version

# 3. 最小化 docker-compose.yml（移除源码挂载）

# 4. 启动测试

# 5. 逐个评估缺失功能（真需要？能配置？能提PR？）

# 6. 只添加通过评估的挂载（≤3文件）

# 7. 文档化决策
```

### 验收标准
- [ ] 镜像来自官方 registry
- [ ] 源码挂载 ≤ 3 个
- [ ] 升级只需改配置 + pull
- [ ] 有文档说明保留/放弃的功能

---

## 反模式

### ❌ "Almost Official"（几乎官方）
用官方镜像 + 挂载整个源码目录 → 自欺欺人

### ❌ "Config Hell"（配置地狱）
50+ 环境变量，大量非标配置 → 考虑 fork

### ❌ "Version Lock"（版本锁定）
因挂载不兼容锁死老版本 → 失去官方同步能力

---

## 总结

**一句话：**  
> "配置或≤3文件解决不了？提PR或接受官方行为。"

**记住：**
- 自建镜像 = 维护负担的开始
- 官方镜像是最大公约数
- 你的需求可能没那么特殊
- Linus：优先用官方，最小化改动，改了提PR

**复杂度目标：**
- 理想：0（纯配置）
- 可接受：≤5（少量挂载）
- 警戒：>5（重新评估）
- 危险：>10（考虑fork或放弃）
